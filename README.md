# racewalk-ai

競走影片的 AI 步態分析：從影片量測觸地／離地事件、騰空時間與膝關節角度。

> **這是輔助分析工具，不是判罰工具。**
> 競走犯規的判定權屬於人類裁判。本系統的輸出一律標示為「疑似／待人工複核」
> 並附信心度，不提供自動失格功能。若要用於任何正式賽會，須另行向該賽會與
> 所屬協會確認採認規定。

完整規劃見 [docs/PLAN.md](docs/PLAN.md)。

## 這個專案在解決什麼

World Athletics 規則 TR54 對競走只有兩條技術要求：不得有**肉眼可見的騰空**，
以及前導腳自觸地到通過垂直支撐位置期間**不得彎膝**。判定完全依賴裁判肉眼、
發生在瞬間、沒有可複查的客觀紀錄。

關鍵在於規則寫的是「**肉眼可見的**騰空」，不是「有沒有騰空」——菁英選手的
騰空時間本來就落在 20–40 毫秒之間，物理上幾乎人人都騰空。所以本系統的核心
輸出是**騰空時間（毫秒）加上量測不確定度**，再與一個可調的可見性門檻比較。
若只回答「有沒有騰空」，會把所有合格選手都標成犯規，工具當場失去意義。

## 網頁版：不用裝任何東西

`web/analyzer.html` 是一個可以直接用瀏覽器開啟的獨立分析工具：選影片 →
自動抓骨架 → 算出觸地、騰空時間與膝角。不需要 Python、不需要命令列。

**影片完全在瀏覽器內處理，不會上傳到任何伺服器。** 這對選手肖像權來說很重要。

```bash
# 下載 repo 後直接用瀏覽器開啟這個檔案即可
open web/analyzer.html          # macOS
start web\analyzer.html         # Windows
```

首次使用需要連網，瀏覽器會從 CDN 取得 MediaPipe 的姿態估計模型（之後會快取）。

### 兩份實作，一組數字

核心演算法有 Python 與 JavaScript 兩份實作——CLI 用前者，網頁版用後者。
兩份若各自演化，同一段影片在兩邊會給出不同的騰空毫秒數，而使用者沒有辦法
知道該相信哪一個。所以 CI 會用同一組軌跡跑兩邊並逐數值比對：

```bash
python3 tools/dump-fixtures.py && node tools/verify-port.mjs
```

實測差異在 1e-13 毫秒的量級，也就是純粹的浮點捨入。

`web/racewalk-core.js` 是唯一來源，`analyzer.html` 由它內嵌產生
（瀏覽器從 `file://` 載入 ES module 會被 CORS 擋，所以必須內嵌）：

```bash
python3 tools/build-web.py           # 重新產生 analyzer.html
python3 tools/build-web.py --check   # 檢查是否同步（CI 用）
```

### 網頁版的限制

- **幀率要自己確認。** 瀏覽器沒有可靠的方式讀出影片幀率。頁面會用極慢速播放
  搭配 `requestVideoFrameCallback` 推算，但這只是參考值——**請以你拍攝時的
  設定為準**。這個值錯了，所有毫秒數都會跟著錯。
- **姿態估計用 MediaPipe**，精度低於 RTMPose。在遮擋、逆光、多人同框的情況下
  會失敗，頁面會把那些影格的信心度標為 0 並提示。
- **逐格 seek 很慢**，2–3 秒的片段大約要等數十秒。

## 快速開始（命令列版）

不需要任何模型權重或 GPU，核心演算法只用 Python 標準函式庫：

```bash
pip install -e ".[dev]"

# 以合成軌跡跑完整條步態管線（真值已知，會一併印出誤差）
racewalk demo

# 幀率消融實驗：用實測數字回答「60 fps 到底夠不夠」
racewalk ablation

# 可疑片段粗篩：看不同幀率下「什麼證得出來、什麼證不出來」
racewalk screen

# 讀取一段真實影片，回報它能回答什麼問題
racewalk check my_video.mp4
```

## 兩種用法，對應兩種畫面

這個專案現在有兩條路徑，因為**它們回答的是不同的問題**。

### 粗篩：「哪幾秒鐘值得看一眼」

適用於比賽轉播、集團行進、機位不理想的畫面——也就是大多數實際拿得到的素材。

粗篩不量精確值，改為輸出**取樣界線**。若觀察到連續 k 格雙腳都離地、取樣間隔
為 Δ，且前後各有一格確定踩地，則騰空時間必然滿足：

```
(k - 1) · Δ  <  騰空時間  <  (k + 1) · Δ
```

這不是估計，是取樣本身推出的邏輯界線，**任何幀率下都成立**。30 fps 看到連續
三格雙腳離地，就能斷言騰空超過 66 ms——不需要任何精度假設。

只在下界超過門檻時才標記，所以：

| 騰空時間 | 240 fps | 60 fps | 30 fps |
|---|---|---|---|
| 30 ms（合規） | 不標記 | 不標記 | 不標記 |
| 45 ms | 標記 | 證明不了 | 證明不了 |
| 90 ms | 標記 | 標記 | 標記 |
| 150 ms | 標記 | 標記 | 標記 |

**低幀率的代價是漏報，不是誤報。** 這是刻意的取捨：裁判看兩次假警報就不會
再用了。`racewalk screen` 可以直接跑出上表。

粗篩另外提供兩個訊號：**膝角**（幾何量，不需要次幀精度，低幀率下反而比騰空
更可靠）與**節奏異常**（與該選手自身中位數比較，對拍攝條件不敏感）。

## 幀率決定精確量測的上限

`racewalk ablation` 的實測結果（合成軌跡，觸地 300 ms、騰空 30 ms、雜訊 1 px）：

| 幀率 | 能力等級 | IC/TO 最大誤差 | 騰空時間 MAE | 可用性 |
|---|---|---|---|---|
| 240 fps | `full` | 0.97 ms | 0.38 ms | 騰空量測可靠 |
| 120 fps | `reduced` | 2.02 ms | 1.98 ms | 可用，須連同誤差判讀 |
| 60 fps | `gait_only` | 6.12 ms | 3.43 ms | 不輸出騰空時間 |
| 30 fps | `gait_only` | 14.46 ms | 21.83 ms | 誤差達騰空本身的 73% |

低於 120 fps 的影片，系統會自動停用騰空相關輸出，只提供膝角、步頻、步長。
**寧可不給答案，不可給錯答案。**

拍攝規格建議見 [docs/CAPTURE_GUIDE.md](docs/CAPTURE_GUIDE.md)。

## 開發

```bash
pytest -q          # 99 個測試，約 0.3 秒
ruff check racewalk tests
```

測試不依賴任何模型或影片檔：合成軌跡的每個 IC/TO 真值都由參數決定，
可以直接量出偵測器誤差。CI 會跑完整測試與消融實驗，精度一旦劣化就會變紅。

### 演算法設計上的取捨

幾個踩過的坑記錄在原始碼註解裡，改動前值得一讀：

- **觸地門檻寬度**（`gait/events.py` 模組開頭）——門檻越寬，TO 偏晚、IC 偏早，
  騰空時間被系統性低估兩倍的偏差。實測門檻 0.25 會造成 ±11 ms 偏差，0.06 則
  小於 1 ms。
- **濾波器的初始狀態**（`signal.py` 的 `_lfilter`）——狀態若從零開始，足部
  座標數百像素的 DC 偏移會在影片開頭產生巨大暫態，足以生出假的觸地事件。
- **鏡像 vs 奇對稱填補**（`signal.py` 的 `filtfilt`）——奇對稱會把雜訊汙染的
  端點放大兩倍灌進濾波器，尾端殘差 0.35 vs 鏡像的 0.09。
- **單腳最短擺動時間**（`gait/events.py` 的 `_merge_short_gaps`）——一隻腳離地後
  不可能在幾毫秒內回到地面，這個物理約束用來把關鍵點掉格和真正的騰空分開。
