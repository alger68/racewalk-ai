# 競走影片 AI 犯規分析系統 — 規劃書

## Context（為什麼做、要解決什麼）

競走（Race Walking）是田徑中唯一「靠裁判肉眼即時判定技術犯規」的項目。World Athletics 規則 TR54 只有兩條技術要求：

1. **不得有肉眼可見的騰空**（loss of contact）— 任一瞬間必須有一腳與地面接觸，且「可見」以人眼為準。
2. **前導腳不得彎膝**（bent knee）— 前腳自觸地瞬間起，到通過身體垂直支撐位置為止，膝關節必須保持伸直。

判罰流程：裁判出示黃牌警示（`~` 代表騰空、`>` 代表彎膝），正式判定則送紅卡給主任裁判；**三位不同裁判各一張紅卡即失格**（部分賽會改用罰時區 Penalty Zone）。

問題在於：判定完全依賴人眼、瞬間、主觀，且菁英選手的騰空時間本來就在 20–40 毫秒之間——**物理上幾乎人人都騰空，差別只在「看不看得見」**。這造成三個真實需求：

- **選手／教練**：訓練時無法量化自己離犯規邊界有多近，只能靠比賽被抓才知道。
- **裁判**：賽後複核與裁判訓練缺乏客觀素材。
- **研究**：缺乏大量、標準化的觸地／離地事件與膝角資料。

本專案要做的，是一套從影片輸入到逐幀量化輸出的分析管線，**先做可信的步態量測，再談犯規判定**。

### 關鍵設計前提（整個專案的成敗點）

> 規則寫的是「**肉眼可見的**騰空」，不是「有沒有騰空」。
> 若系統只回答 airborne=true/false，會把幾乎所有合格選手都標成犯規，直接失去可用性。
>
> 因此系統的核心輸出必須是 **騰空時間（毫秒）+ 量測不確定度**，再與一個「可見性門檻」（預設 40 ms，可調）比較，並永遠附上信心度與證據影格。這條原則貫穿整份規劃。

### 定位與界線（明確寫進 README 與 UI）

- 本系統是**輔助分析工具**，不是判罰工具。正式比賽的判定權屬於人類裁判，規則亦未授權以儀器判定。
- 任何「犯規」字樣的輸出一律標示為「**疑似 / 待人工複核**」，並附信心度。
- 若未來要對接賽會使用，須另行確認該賽會與所屬協會的採認規定（此點需向中華民國田徑協會／World Athletics 查證，本規劃不作假設）。

### 已確認的需求（本次對話）

| 項目 | 決定 |
|---|---|
| 使用情境 | 三者都要，但**分階段**：訓練回饋 → 裁判輔助 → 研究輸出 |

## 一、系統節點圖（Processing Pipeline）

每個節點都是獨立可測試的模組，輸入輸出以 JSON / Parquet 明確定義，可單獨替換模型而不動下游。

```
[N0] 影片輸入
      │  mp4 / mov，記錄 fps、解析度、快門、機位 metadata
      ▼
[N1] 解碼與正規化
      │  ffmpeg 逐幀解碼｜時間戳校正（VFR→CFR）｜鏡頭畸變校正
      │  地面線標定（homography，用場地標記線推算像素↔公尺）
      ▼
[N2] 人體偵測與追蹤
      │  YOLO 系列偵測 + ByteTrack/BoT-SORT 指派 track_id
      ▼
[N3] 選手識別（賽事模式才需要）
      │  號碼布 ROI 裁切 → OCR；失敗時以衣著外觀特徵 re-ID 續接
      ▼
[N4] 2D 姿態估計
      │  RTMPose / ViTPose，取髖、膝、踝、腳跟、腳尖（26 點格式含足部）
      │  每個關節點輸出座標 + 信心度
      ▼
[N5] 時序平滑與濾波
      │  Butterworth 低通（截止 ~10–12 Hz）｜低信心點內插
      │  ★ 不可過度平滑：會抹掉觸地瞬間的速度轉折
      ▼
[N6] 步態事件偵測  ← ★ MVP 的核心節點
      │  IC 觸地 / TO 離地 時刻（次幀精度，用速度零交越線性內插）
      │  方法 A：足部垂直速度極值 + 足部到地面線距離門檻
      │  方法 B：以 TCN/1D-CNN 對關鍵點序列做事件分類（有標註資料後再上）
      ▼
[N7] 特徵計算
      │  騰空時間 flight_time_ms（雙腳皆離地的區間）
      │  觸地時間、步頻、步長、速度
      │  膝角序列 θ(t)；觸地→垂直支撐期間的最小膝角 min_knee_angle
      ▼
[N8] 規則引擎（第二版才啟用）
      │  騰空：flight_time > 可見性門檻(預設 40ms) 且 量測不確定度 < X → 疑似
      │  彎膝：min_knee_angle < 門檻(預設 175°) → 疑似
      │  每筆輸出 confidence + 依據幀號
      ▼
[N9] 證據與報表
      │  切出前後 0.5s 片段 + 骨架/角度疊圖｜逐步伐 CSV｜趨勢圖
      ▼
[N10] 人工複核與回饋
      │  複核介面標記「同意/不同意」→ 回流成訓練標註（主動學習）
```

### 各節點的資料契約（先定好，之後不用重構）

```
frames.parquet      frame_idx, t_ms, track_id, kp_x[26], kp_y[26], kp_conf[26]
events.parquet      track_id, event(IC|TO), foot(L|R), t_ms, confidence, method
steps.parquet       track_id, step_idx, ic_t, to_t, contact_ms, flight_ms,
                    min_knee_angle, knee_angle_at_ic, cadence, step_len_m, uncertainty_ms
findings.json       track_id, rule(loss_of_contact|bent_knee), t_ms, severity,
                    confidence, evidence_clip, reviewed_by, review_result
```

## 二、開發里程碑（Milestones）

以「可驗收的量化門檻」定義每個節點，未達門檻不進下一階段。總期程約 **18–22 週**（單人兼職開發估算；全職可壓縮至 10–12 週）。

### M0 — 規格與資料蒐集（2 週）
- 確認拍攝規格（見第三節），實地試拍 pilot 影片。
- 建立標註規範文件（IC/TO 的定義、模糊影格處理原則、雙人標註一致性檢查）。
- 整理 TR54 規則原文與判定情境對照表。
- **驗收**：完成 ≥ 30 段試拍（不同選手／速度／光線），兩位標註者對 IC/TO 的一致性 ≤ 1 影格。

### M1 — 資料管線與標註工具（2–3 週）
- ffmpeg 解碼、時間戳正規化、鏡頭標定腳本。
- 逐幀標註工具（可用 CVAT，或自製：影格步進 + 鍵盤標記 IC/TO）。
- **驗收**：100–200 步伐的人工 IC/TO ground truth 入庫；管線可重跑且結果可重現。

### M2 — 偵測、追蹤、姿態基線（3 週）
- 接上 YOLO + ByteTrack + RTMPose，跑通 N2–N5。
- **驗收**：下肢關鍵點 PCK@0.05 ≥ 0.90；單人場景追蹤不斷線；多人場景 IDF1 ≥ 0.85。

### M3 — 步態事件偵測 ★ MVP 交付（3–4 週）
- 實作 N6、N7 的觸地/離地與步態指標。
- **驗收（這是整個專案最重要的數字）**：
  - IC/TO 時刻誤差 ≤ 1 影格（240fps 下約 ±4 ms）
  - 騰空時間 MAE ≤ 8 ms，且系統能對每筆估計輸出不確定度
  - 步頻誤差 < 2%
- **交付**：CLI 工具 `racewalk analyze video.mp4` → 輸出 steps.parquet + 疊圖影片 + 趨勢圖。此時已能給教練用。

### M4 — 膝角量測（2 週）
- 膝關節角度序列、觸地→垂直支撐期間最小膝角；處理 2D 投影誤差（非矢狀面時標記為低信心）。
- **驗收**：膝角 MAE ≤ 3°（對照人工逐幀量角）；離面旋轉超過閾值時能自動降信心並提示。

### M5 — 規則引擎與複核介面（4 週）
- N8 規則引擎（門檻可調、每筆附信心度）+ N9 證據片段 + N10 複核 Web 介面。
- **驗收**：在一組有裁判紅卡紀錄的比賽影片上，疑似判定對裁判紅卡的召回率 ≥ 0.8、誤報率可接受（先以「每位選手每 km 誤報數」呈現，不追求單幀精度）。
- **注意**：這一階段的目標是「與裁判判斷可對話」，不是「取代裁判」。若召回率上不去，正確反應是調整門檻與呈現方式，不是硬調成好看的數字。

### M6 — 賽事／現場模式（4 週，選配）
- 多機位、長時間影片分段處理、選手號碼識別、批次報表、（若需要）近即時處理。
- **驗收**：一場 20km 比賽影片可在合理時間內批次跑完並產出每位選手報表。

## 三、拍攝設備規格建議（你指定要我建議的部分）

騰空時間只有 20–40 ms，**幀率決定了這個專案的上限**。

| 條件 | 建議規格 | 理由 |
|---|---|---|
| **幀率** | **≥ 240 fps**（每幀 4.2 ms）。120 fps 為下限，60 fps 不足以做騰空判定 | 40 ms 的騰空在 240fps 下有約 10 幀，可靠；60fps 只有 2–3 幀 |
| **快門速度** | ≥ 1/1000 s（越快越好） | 動態模糊會讓腳與地面的接觸邊界糊掉，直接毀掉 IC/TO 精度 |
| **解析度** | 1080p 即可；優先把幀率與快門給足 | 4K@30fps 對本專案毫無用處 |
| **感光元件** | 有預算優先選 **global shutter** 工業相機 | rolling shutter 會讓快速移動的腳部變形，影響角度量測 |
| **機位** | 側向、光軸**垂直於行進方向**，鏡頭高度約 0.8–1.0 m（近髖高），距離賽道 5–8 m | 矢狀面拍攝才能正確量膝角；垂直可減少投影誤差 |
| **鏡頭** | 中焦段（等效 50–85mm），避免廣角 | 廣角桶形變形會扭曲角度；必須做棋盤格標定 |
| **光線** | 戶外日光最佳；室內需 ≥ 1000 lux | 1/1000s 快門非常吃光，光不足就只能拉 ISO 或降快門，兩者都傷判定 |
| **地面參考** | 地面貼 1 m 間距標記帶，入鏡 | 用於 homography 標定（像素→公尺）與地面線推算 |
| **背景** | 乾淨、與選手服裝對比明顯 | 提升姿態估計與足部邊界穩定度 |

**分級方案：**

- **入門（$0）**：iPhone / Android 慢動作 240fps @1080p，三腳架固定。實測可用，但需在**充足日光**下拍，且要關閉自動對焦漂移。**建議從這裡開始驗證管線**。
- **標準（約 2–5 萬台幣）**：具 240fps 的運動相機或無反 + 定焦鏡 + 穩固三腳架 + 補光。
- **進階（10 萬以上）**：global shutter 工業相機（如 FLIR/Basler 240–500fps）+ 硬體同步兩機位（側向 + 斜後 45°），可做 2D→3D 三角量測，大幅降低投影誤差。

**降級處理原則（要寫進程式）**：系統讀到影片 metadata 後自動判定能力等級。< 120 fps 的影片，騰空相關輸出一律標示 `unreliable`，只提供膝角與步頻步長等較穩健的指標——**寧可不給答案，不可給錯答案**。

## 六、風險與對策

| 風險 | 影響 | 對策 |
|---|---|---|
| **「肉眼可見」無法客觀定義** | 犯規判定失去依據 | 不定義，改為輸出騰空毫秒數 + 可調門檻；門檻由使用者/裁判設定，系統只負責量測 |
| 幀率不足導致騰空判定不可靠 | 核心功能失效 | metadata 自動分級；低幀率影片停用騰空輸出而非硬給 |
| 2D 姿態的投影誤差（非矢狀面） | 膝角量測偏差 | 偵測離面角度，超標降信心；進階版用雙機位三角量測 |
| 多人重疊遮擋（集團行進） | 追蹤斷線、關節點錯亂 | 賽事模式加號碼布 re-ID；遮擋期間輸出標記為 gap 而非內插猜測 |
| 標註主觀性（人工 IC/TO 本身也有誤差） | ground truth 不可靠 | 雙人獨立標註 + 一致性檢查；必要時以高速攝影 + 測力板做小樣本校準 |
| **把工具當判罰依據** | 爭議、傷害選手權益 | UI 與輸出全面標示「輔助分析、非正式判定」；不提供「自動失格」功能 |
| 選手肖像與個資 | 法律風險 | 影片不進版控；訓練資料取得選手同意；公開展示需去識別化 |

## 七、驗證方式（End-to-End）

1. **合成影片回歸測試**：以已知 IC/TO 時刻的合成骨架動畫渲染成影片，跑完整管線，驗證事件偵測誤差在 1 影格內。此測試進 CI，每次提交都跑。
2. **人工標註對照**：`racewalk eval --gt annotations.json --pred steps.parquet` 輸出 IC/TO 誤差分佈、騰空時間 Bland–Altman 圖、膝角 MAE。
3. **幀率消融實驗**：同一段 240fps 影片降採樣到 120/60/30 fps，量化各項指標的劣化曲線——**用實測數字回答「60fps 到底夠不夠」，不用猜的**。
4. **人工目視複核**：隨機抽 20 步伐，用複核介面逐幀確認疊圖的觸地時刻與骨架是否合理。
5. **裁判對照（M5）**：取有紅卡紀錄的比賽影片，比對系統疑似標記與裁判判定的時間位置。
