## 一、Context（為什麼做）

競走是田徑中唯一「靠裁判肉眼即時判定技術犯規」的項目。World Athletics
規則 TR54 只有兩條技術要求：

1. **不得有肉眼可見的騰空**（loss of contact），裁判黃牌符號 `~`
2. **前導腳自觸地到通過身體垂直位置不得彎膝**（bent knee），符號 `>`

三位不同裁判各一張紅卡即失格（部分賽會改用罰時區）。詳見 `docs/RULES.md`。

問題在於判定完全依賴人眼、瞬間、主觀。而**菁英選手的騰空時間本來就在
20–40 ms 之間——物理上幾乎人人都騰空，差別只在看不看得見**。

### 貫穿全案的設計前提

> 規則寫的是「**肉眼可見的**騰空」，不是「有沒有騰空」。
> 一個只回答 airborne=true/false 的系統，會把幾乎所有合格選手標成犯規，
> 直接失去可用性。

這條前提現在有了具體實作：`site/core.js` 的 `DETECTION_BANDS`
不比大小，而是把騰空長度對應到「文獻報告過裁判看不看得見」。

### 定位與界線

- 本系統是**輔助分析工具**，不是判罰工具。
- 輸出一律標示「疑似／待人工複核」。
- **規則面的支持**：TR54.7.8（2026）只授權裁判用手持裝置**登錄**自己的判定；
  2022 年起更禁止鞋內含 sensing/intelligent 技術，而在此之前 IAAF 曾試驗
  電子鞋墊。也就是說國際總會**試過**用感測器判觸地，現行規範是往回收的。
  這不是本專案的自我設限，是現行國際規範的方向。出處與核對狀態見
  `docs/RULES.md`。

## 二、現況：實際長成什麼樣

**不是原規劃的 Python 管線。** 目前是一個純瀏覽器工具（RaceWalk Lab 3.0.5），
影片不上傳、不進版控，全部在使用者機器上跑完。

```
[N0] 影片輸入          <video> 直接讀本機檔；不解碼成影格檔
      ▼
[N1] 取樣              以 sampleFps 逐時間點抓畫面；無 VFR 校正、無鏡頭標定
      ▼
[N2] 姿態與目標鎖定    MediaPipe Pose（33 點，含 heel/foot_index）
      │                site/target-lock.js：使用者點選指定選手，嚴格關聯不變式
      │                site/continuity.js：取不到值時繼續掃描，不中止整段
      ▼
[N3] 地面線            estimateGroundY：取足部高度 96 百分位（保守）
      ▼
[N4] 訊號處理          lowpass（零相位、鏡像 padding、狀態參考 x[0]）
      │                residualNoise → 雜訊自適應觸地門檻
      │                fillGaps、cleanRuns（MIN_CONTACT_MS / MIN_SWING_MS）
      ▼
[N5] 觸地三態          contactStates：contact / off / unknown
      │                ★ unknown 絕不可讀成 off，否則遮擋會被製造成騰空
      ▼
[N6] 取樣界線          flightIntervals：lowerMs=(k-1)Δ 嚴謹；upperMs 非嚴謹
      ▼
[N7] 規則對應量        supportKnee（觸地→verticalSupportIndex 的最小膝角）
      ▼
[N8] 可見性分帶        judgeDetection：文獻三帶，不是門檻比大小
      ▼
[N9] 報表              schema 5；每段附 detection、證據敘述與出處
```

### 已建立的核心不變式

這些是 `tests/contact.test.mjs`（34 例）守住的性質，不是願望：

| 不變式 | 為什麼重要 |
|---|---|
| `lowerMs` 永不超過真值 | 這是整個粗篩的可信度來源，任何幀率都成立 |
| `upperMs` **不是**嚴謹上界 | 門檻有寬度，剛離地的腳仍被標 contact；已寫成測試記錄 |
| 端點／unknown 夾住的區段一律丟棄 | 沒觀察到起訖就推不出界線 |
| 遮擋不會變成騰空 | 三態遮罩的唯一目的 |
| 30 ms 合規騰空在 240/120/60/30 fps 都不被標記 | 低幀率以**漏報**而非誤報的形式失去靈敏度 |
| 120 ms 騰空在四種幀率都證得出來 | 粗篩的下限能力 |

## 三、下一步（依序，不可跳）

### ★ P0 — 實拍與校準（唯一的阻塞項）

**到目前為止的每一個數字都來自合成資料。** 沒有任何一段真實影片跑過完整流程。
下列參數全部未校準：

- 觸地門檻 `0.018`（正規化座標）
- 支撐期膝角的犯規判準——**目前程式裡根本沒有這個門檻**，報表只給角度，由人判讀；
  要訂一個數字出來，必須先有實拍與裁判對照
- `DETECTION_BANDS` 的三帶邊界對應到真實裁判行為的程度
- 非矢狀面拍攝造成的膝角偏差量

要做的事：依 `docs/CAPTURE_GUIDE.md` 試拍 10–30 段（手機 240 fps 慢動作即可，
但要確認不是後製轉出的假慢動作——指南裡有 `ffprobe` 檢查法），跑過工具，
逐段人工核對觸地時刻。

**驗收**：IC/TO 時刻與人工標註誤差 ≤ 1 影格；`lowerMs` 的嚴謹性在真實影片上
不被推翻（沒有任何一段實際騰空短於系統給的下界）。

### P1 — 裁判紅卡對照

取有紅卡紀錄的比賽影片，逐張紅卡對照系統算出的 `lowerMs` 與分帶。

**驗收**：不是追求高召回率，而是回答「分帶與裁判行為對不對得起來」。
若對不起來，正確反應是**修分帶或承認測不到**，不是把門檻調到好看。

### P2 — 集團場景的目標鎖定

真實比賽畫面（使用者提供的那張截圖）暴露了遮擋與多人交錯的問題。
3.0.4/3.0.5 已做了嚴格關聯與連續性恢復，但**那不是身分保證**。

**驗收**：一段有超車與遮擋的實拍，目標不會在沒有明示重選的情況下換人。

### P3 — 證據輸出

每段疑似區間切出前後 0.5 s 影片 + 骨架疊圖，供人工複查。目前只有時間碼。

### P4（選配）— 研究輸出

逐步伐 CSV／Parquet 匯出，供研究使用。

## 四、拍攝設備規格

完整版見 `docs/CAPTURE_GUIDE.md`。重點只有一句：

> **騰空只有 20–40 ms，幀率決定這個專案的上限。**

- ≥ 240 fps（每幀 4.2 ms）；120 fps 為下限；60 fps 不足以做騰空粗篩
- 快門 ≥ 1/1000 s——動態模糊會糊掉腳與地面的接觸邊界
- 1080p 足夠；**4K@30fps 對本專案毫無用處**
- 側向機位、光軸垂直於行進方向、鏡頭高度約 0.8–1.0 m
- 入門方案 $0：手機 240 fps 慢動作 + 三腳架 + 充足日光。**建議從這裡開始**

## 六、原規劃被推翻的部分

保留這節是因為這些是花代價換到的。

**Python + ffmpeg + RTMPose + FastAPI + React 管線 → 純瀏覽器工具。**
架構整個換掉。代價是失去 ffmpeg 的 VFR 校正、鏡頭標定與 homography；
換到的是影片完全不離開使用者機器，以及零安裝。就本專案的個資風險而言
這筆交易划算，但**像素→公尺的換算目前做不到**，步長與速度因此不在輸出裡。

**「先做精確量測」→「先做可疑片段粗篩」。** 這是最大的一次轉向。
原規劃的 M3 驗收寫「騰空時間 MAE ≤ 8 ms」——那要求系統給出點估計。
實際上取樣界線給得出**嚴謹的下界**，卻給不出嚴謹的上界。
與其給一個沒有保證的點估計，不如給一個保證成立的下界。粗篩因此比量測誠實。

**低通截止 10–12 Hz → 50 Hz。** 步態分析的慣用值會直接抹掉 20–40 ms 的
觸地轉折。這在原規劃裡被寫成「★ 不可過度平滑」，但給的數字本身就是過度平滑。

**固定觸地門檻 → 雜訊自適應。** 固定 0.25 帶來 ±11 ms 偏差；掃到 0.06 後
降到 1 ms 以內，再加上以二階差分估計的殘餘雜訊動態放寬。

**斜率外插補償 → 移除。** 足部軌跡在接近地面時變陡，線性外插過度修正約 66%。
這個失敗被記錄下來而不是留在程式裡。

**40 ms 硬門檻 → 文獻分帶。** 見 `docs/RULES.md`。

**整段最小膝角 → 支撐期最小膝角。** 擺動期彎膝是正常動作，混進去得到的是
一個與 TR54 無關的數字。

**原時程 18–22 週。** 這個估計建立在上面那條管線上，已無意義。現在的
瓶頸不是開發工時，是**還沒有一段真實影片**。
